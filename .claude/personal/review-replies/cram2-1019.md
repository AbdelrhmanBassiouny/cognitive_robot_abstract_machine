### r4646330164 — spatial_types.py:499, `SymbolicAxisCoordinates` (resolve)
> adding this class for just this method is too much … can move up the interface hierarchy

Done (387b26e3, 6501202762): `SymbolicAxisCoordinates` is gone. The axes now belong to the kind of frame: `AffineFrame.axes`, with `CartesianFrame3Dimensional` naming x, y, z and a pixel frame u, v. `AxisCoordinates` reads and builds every value, symbolic or not, through those axes, and gives a new value its coordinate system through `CoordinateRepresentation.from_constructor_arguments`, which `SymbolicSpatialValue` overrides once to pass the `reference_frame` keyword instead of `coordinate_system` (5bfec7cc). The symbolic points and vectors declare nothing for it: their `x`, `y`, `z` properties already meet the contract, and a type missing an axis fails where it is defined (`MissingAxisCoordinatesError`).

### r4646302991 — spatial_types.py:1344, `CrossProductVector` as a base (resolve)
> what is this? I don't like this as a base class.

Removed in 387b26e3. A cross product exists only in an oriented, three-dimensional Cartesian frame, so it now belongs to the kind of frame, just as the inner product does: `CartesianFrame3Dimensional.cross_product(first=..., second=...)` computes it from the coordinates, and `AffineFrame.cross_product` raises `FrameHasNoCrossProductError`. `Vector.cross(other=...)` asks its frame kind, the way `Vector.dot` does, so a 2D or pixel vector raises.

### r4646402733 — vector.py:123 (resolve)
> how many classes have this as a base? and can it be joined with any of the existing interfaces like Vector

Only `Vector3Dimensional` had it, and the casadi-free `MotionVectorPair` used it for the adjoint action. It is joined into `Vector` now (387b26e3): `cross` is on `Vector`, measured by the frame kind, and `MotionVectorPair` binds a plain `Vector`. `CrossProductVector` and `GenericCrossProductVector` are gone.

### r4644985221 — coordinate_system.py:244, `homogeneous_weight` (resolve)
> Should this be bool?

Yes, done in 7c0b1bda: it is the bool classproperty `has_position` now. A `Point` has a position and a `Vector` has none, and `apply_transformation` appends `int(has_position)` as the homogeneous weight, so the weight is built in one place and nothing can give a weight other than 0 or 1.

### r4641331500 — giskardpy cartesian_tasks.py:674 (resolve)
> why do we have to do `.rotation_matrix` here?

Because `T @ R` is now a transformation: composing a rotation with a transformation that has a translation can leave SO(3), so it keeps `T`'s translation instead of silently dropping it. The task wants the goal orientation expressed in root, which is the rotation part of `root_T_reference` composed with it: `root_T_reference.rotation_matrix @ goal_orientation` is a rotation, and it still checks that the goal is given in the transformation's child frame.

### r4630668094 — spatial_types.py:1735 (ichumuh) (leave for ichumuh to resolve)
> Point3 was much cooler … super difficult to implement a new space by hand

The names got shorter again: `Point3Dimensional` (no `Cartesian` prefix), and the dimension is only spelled where a 2D counterpart exists. Adding a space got much simpler: `Point` and `Vector` are one class each and do the arithmetic, the frame checks and the change of frame. A new space's frame kind names its axes, and its point and vector only declare one field per axis. The README's *Adding a space* section now adds camera pixels end to end, with a crop-and-resize change between two images' pixels, and a test runs it. The only code with logic is the change's math (`apply_to_homogeneous_coordinates`, `inverse`, `@`).

## LucaKro's review (changes requested, 2026-11-19)
> every SE(2) change between two different frames breaks its own contract, even for coplanar frames

If not answered yet: two `EmbeddedPlane`s are equal when they lie in one space and share their points, not when their frames are equal, so an SE(2) change between coplanar frames such as the floor and a robot base stays within one plane, as `RigidCoordinateChange` requires. `CartesianFrame3Dimensional.compare_embedded_plane` says how two frames' planes lie.
