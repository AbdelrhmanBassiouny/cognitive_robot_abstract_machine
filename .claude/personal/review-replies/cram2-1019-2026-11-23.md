# Replies for cram2#1019, ichumuh's review of 2026-11-23 (code at f0712a33)

## 1. `cartesian_frame_3_dimensional.py:39` - "i don't see the point of this class ... you accept UNKNOWN without checking"

You were right about `UNKNOWN`: it skipped the check exactly where nothing could
verify the frames (a frame in no world, or a transformation with free variables).
44c4f534 closes that:

- A planar transformation between frames whose planes are not known now raises
  `UnknownEmbeddedPlaneRelationError` instead of passing.
- `from_transformation` of a transformation that is not constant reads the relation
  from its frames; if it has no child frame, it raises too.

I'd keep the plane comparison rather than require the exact same frame: SE(2)
between `floor` and `robot_base` is the main use of 2D transforms (navigation), and
that is two different frames on one plane. The enum is what tells the caller *why*
no planar change exists (different planes vs. mirrored), so it picks the error.

## 2. `cartesian_frame_3_dimensional.py:95` - "shouldn't this return a Vector3?"

Half right: `Vector` was too loose, but `Vector3Dimensional` is too narrow, because a
numeric vector type in a 3D Cartesian frame is a vector of that frame too. It
returns the type of its operands now (`first: GenericVector -> GenericVector`), so
`cross_product` of two `Vector3Dimensional` is a `Vector3Dimensional` for a type
checker as well (asserted in `static_types.py`). Fixed in 44c4f534.

## 3. `motion_vector_pair.py:21` - "isn't that our twist class?"

Twist implements it. `MotionVectorPair` is the casadi-free part: a pair of
vectors (how a body turns, how the origin moves) and how a change of frame moves
it, the adjoint action. `Twist`, `ScrewAxis` and `Displacement` are its casadi
implementations, so the adjoint action is written once and not per class. Main is
merged in now (9f5540e0, with Luca's docs PR #1043).

## 4. `coordinate_system.py:335` - "smells hacky ... only a position and vector subclass"

It is the homogeneous-coordinates model itself, not an assumption about
subclasses: a value's last homogeneous coordinate is 1 if a change shifts it with
the origin (a position) and 0 if it doesn't (an offset/direction). A pose or a
twist isn't an `AxisCoordinates` at all; each implements `apply_transformation`
its own way. `has_position` only names which of the two homogeneous cases a value
is, so a new value type answers one question instead of re-implementing the move.

## 5. `coordinate_system.py:421` - "weight?"

That was two names for one thing. 44c4f534 uses one: the docstring now says the
coordinates are followed by 1 if the value has a position and 0 if not, and the
README's and the tests' implementations name that entry `has_position`.

## 6. `coordinate_system.py:414` - "why is this a tuple?"

Correction to my earlier reply: users do write it. Every new change implements
this method (the README's `CropAndResize` does). It's a tuple because it has to
carry homogeneous coordinates of any dimension and of any coordinate type, floats
or `sm.Scalar`, and the change, not the value, decides what each entry means. The
values themselves never expose a tuple: `PixelPoint(u=..., v=...)`.

## 7. `coordinate_system.py:413` - "isn't that a transform?"

It's the one primitive a change implements, applied to raw homogeneous
coordinates; `apply_transformation` and `@` on a value are built on it. The casadi
transformations implement the same method (`spatial_types.py:375`), so there is one
code path, not two.

## 8. `spatial_types.py:402` - "why is operation not https://docs.python.org/3/library/operator.html?"

It was only a label for the error message, and a bare string was the wrong type
for it. 44c4f534 replaces it with the `MathematicalOperation` StrEnum
(`MATRIX_MULTIPLICATION`, `DOT_PRODUCT`, `CROSS_PRODUCT`) on
`UnsupportedOperationError`. `operator` wouldn't cover it: there is no `operator`
function for dot or cross. Applying a change no longer takes an operation argument
at all, which also fixes `T @ x` reporting itself as "dot".

## 9. `coordinate_system.py:109` - "why does this implement the norm? that's the euclidean norm"

Agreed that the frame shouldn't implement it. f0712a33 removes `norm` and
`distance` from the frames: `Vector.norm()` is the square root of the vector's inner
product with itself, the norm any inner product induces, and the kind of frame now
only decides the inner product (`CartesianFrame` sums the coordinate products, an
affine kind raises). I also corrected our wording in 44c4f534: an affine frame in a
Euclidean space does have lengths, through the lengths and angles of its axes; its
coordinates alone just don't give them.

## 10. `coordinate_system.py:125` - "this assumes euclidean space too"

Gone from the frame in f0712a33: `point.euclidean_distance(other)` is the length of
`point - other`, which holds in any normed space. The only Euclidean assumption left
is `CartesianFrame.inner_product`, and an affine kind of frame raises
`FrameMeasuresNoLengthsError` there.

## 11. `coordinate_system.py:128` - "cross product is only defined in 3d space. and again feels out of place for in frames"

Agreed on 3D: only `CartesianFrame3Dimensional` implements it; every other kind
raises `FrameHasNoCrossProductError`. It stays with the frame because its sign
depends on the frame's orientation: the same coordinates give opposite cross
products in a right-handed and a left-handed frame, and handedness is a property of
the frame, not of the vector. After f0712a33 the frame keeps only the two operations
that depend on it: the inner product (its metric) and the cross product (its
orientation). Everything else, length and distance included, is computed on the
values.

## 12. `spatial_types.py:1691` - "Point3 was much cooler ... super difficult to implement a new space by hand"

(Your meme reply stays; add:) To make it concrete: `Point3Dimensional` now has two
bases (`SymbolicSpatialValue`, `Point[Vector3Dimensional]`). A new space is five
declarations and one change: the README's *Adding a space* adds camera pixels in
about 25 lines plus a 40-line change, and the test suite runs it. The one thing
still easy to get wrong is a hand-written `inverse` and `@`; nothing checks
`change.inverse() @ change` except each space's own tests, and a shared law test
would.
